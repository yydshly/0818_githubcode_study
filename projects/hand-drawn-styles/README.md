## 一句话结论

它不是图像模型，而是图像模型之前的一层视觉编排：Agent 负责理解需求和选风格，协议负责限制输入，配方负责描述视觉语言，渲染器负责原样组装，外部图像模型才真正出图。

## 研究目标

1. 用上游真实样图展示 19 套配方能覆盖的效果类型。
2. 从 `SKILL.md`、`PROTOCOL.md`、`STYLES.md`、`render_prompt.py` 和回归测试解释实现原理。
3. 明确它对我们的价值是“可执行视觉合同”，而不是新的生图算法。
4. 在不复制上游风格规则的前提下，增加适合研究封面、原理讲解、结论信息图、项目里程碑和团队故事卡的日常场景路由。

## 我们增加了什么

上游负责“风格怎么画”，我们的扩展只负责“什么时候用哪一种风格”：

| 我们的日常场景 | 推荐风格 | 原因 |
| --- | --- | --- |
| 研究方法拆解 | 1 极简线条、4 小豆人信息图 | 多格结构适合解释步骤和关系 |
| 结论摘要卡 | 4 小豆人、18 暖色扁平绘本 | 一个强调信息，一个强调传播视觉 |

| 里程碑故事 | 10 情绪叙事淡彩速写 | 能把抽象进度转成单一情绪场景 |
| 团队/家庭故事卡 | 3.1 潦草蜡笔 | 通过锚点和三阶段编辑追求连续一致 |

日常扩展层只输出上游风格编号、内容、文字、比例和调用纪律，不维护第二份线条、色板、五官或材质规则。

## 研究边界

- 上游本身不调用图像模型；展厅展示的是上游已有样图和 Prompt 编排演示。
- 普通风格的最终效果依赖具体图像模型；“工具无关”不等于跨模型输出完全一致。
- 3.1 正式生产不能只复制 Prompt，必须附锚点并完成三阶段工作流。
- 上游基准主要是作者人工对照，不能视为大样本或盲测结论。
- MIT 许可覆盖仓库代码和文档，不等于为所有命名风格的商业使用提供额外权利保证。

## 上游测试观察

在 Windows 上直接执行当前上游测试得到 `18/19`：渲染、锚点与三阶段合同均可工作，唯一失败是 `test_rawkid_alias_uses_current_3_1_anchor_contract` 用正斜杠字符串断言绝对路径，而 Windows 返回反斜杠。该问题属于测试的跨平台路径比较缺陷，不是锚点丢失；固定的上游 submodule 未做修改。我们的项目验收通过实际文件、合同 ID 与阶段顺序验证同一路径。

另一个未被现有测试覆盖的问题是：1号配方把段落标签 `【最重要·硬性负向约束】` 写成与占位符相同的括号形式，渲染器会把它识别成额外必填变量。直接按文档只传 `N` 和 `分镜列表` 会失败。展厅仍可展示上游1号样图，但在上游修正标签或解析规则前，不把1号CLI渲染宣称为无障碍可用。

## 上游更新方式

先检查新版本的编号、配方占位符、视觉锚点和工作流合同，再更新 submodule。不要直接追踪 `main` 后自动覆盖当前研究结论。
