## 1. 研究问题

每份报告必须回答四个问题：

1. 项目真实能做什么？
2. 它通过什么机制做到？
3. 它对谁、在什么条件下有用？
4. 在当前项目背景中应该采用、改造、参考还是放弃？

## 2. 证据等级与能力状态

### 证据等级

| 等级 | 证据 | 使用方式 |
| --- | --- | --- |
| A | 本地执行、源码、测试、CI、发布产物、许可证 | 可支撑“已验证”，但必须说明环境与覆盖范围 |
| B | 上游 README、官方文档、官方演示、维护者 issue/discussion | 可支撑“官方宣称”，不能替代本地验证 |
| C | 第三方文章、社区评论、非维护者示例 | 只作线索，关键判断需要更强证据交叉验证 |

### 能力状态

| 状态 | 定义 | 报告措辞 |
| --- | --- | --- |
| `verified` | 在固定 commit 和记录环境中实际运行成功 | “已在……条件下验证” |
| `declared` | 上游明确描述，但本次没有完成运行验证 | “上游宣称；本次未验证” |
| `external` | 依赖仓库外工具、凭据、服务或宿主能力 | “需要外部依赖；仓库本身不提供” |
| `gap` | 宣称、方法或实现之间存在可复现缺口 | “当前实现存在……缺口” |

状态不是分数。一个能力可以同时包含已验证的本地部分和外部依赖部分，应拆成两条记录。

## 3. 五层原理模型

按以下顺序解释项目，避免只列技术栈：

1. **触发与输入**：什么请求、文件、事件或数据启动系统？
2. **路由与编排**：如何选择模式、阶段、工具和失败分支？
3. **核心转换**：真正产生价值的是规则、算法、模型、提示词还是数据管道？
4. **验证与约束**：有哪些 schema、测试、质量门禁、权限或人工复核？
5. **产物与反馈**：输出什么，如何复用、部署、比较或继续迭代？

每层至少引用一个文件、命令或可观察产物。若某层不存在，明确写“未提供”，不要脑补架构。

## 4. 适配判断

用四类结论之一收束：

- **采用**：直接使用收益高，外部依赖与风险可接受。
- **改造**：核心机制有价值，但领域假设、平台或交付形式需替换。
- **参考**：方法论值得借鉴，直接引入的维护成本高于收益。
- **放弃**：无法验证关键能力、许可不兼容或不解决当前问题。

结论至少比较：目标用户、输入数据、运行环境、可验证性、维护成本、许可证和与现有流程的连接点。

## 5. 扩展设计

扩展必须保留一个上游不变量并替换一个领域假设：

```text
上游不变量：证据分级 + 路由 + 对抗验证 + 单一事实源
领域替换：行业/公司对象 → GitHub 仓库对象
当前闭环：仓库 URL → 获取源码 → 验证能力 → 解释原理 → 判断适配 → 生成展示 → 更新主索引
```

最小扩展需要：明确触发、结构化输入、一个确定性脚本、一个真实样本、一个失败样本、可追溯输出和父索引入口。

## 6. 失败模式

- README 写了就当成已实现；
- 测试通过就推断所有业务能力可用；
- 忽略环境变量、外部 CLI、登录态和付费服务；
- 只画架构图，不追踪真实调用路径；
- 复制上游代码却丢失许可证或提交历史；
- 扩展只换名字，没有连接当前用户流程；
- 结论没有推翻条件，或把个人偏好伪装成事实。
